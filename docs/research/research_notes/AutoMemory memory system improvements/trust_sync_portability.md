# Trust, provenance, poisoning, sync, backup and portability for a shared multi-agent, multi-machine memory (state of the art 2025–2026)

Research date: 2026-11-12. Scope: what better systems do and what standards exist, so a local-first memory (SQLite, encrypted delta files in a private git remote, five trust tiers, quarantine, audit ledger, password gate) can be more trustworthy, portable and recoverable. Measured results are marked **[measured]**; everything else is design opinion or documentation.

Method note: web search plus fetch of primary pages where possible. A rate limit cut the last batch (ICML 2026 paper full text, EMNLP 2026 Findings shared-pool paper, Litestream migration guide, Obsidian key details beyond the security page); those appear in Gaps rather than as claims.

## Key question 1: Provenance and trust models for multi-agent memory; measured results of trust tiers and quarantine against poisoning

### Takeaway
Shipping memory products label scope (user/agent/session) far more than author or trust, and none of the surveyed ones (Letta, mem0, Zep, OpenViking, the MCP reference memory server) exposes a per-item trust tier or quarantine. The 2026 measurements are sobering: content screening does not catch plainly worded false statements, and an additive "provenance weight" at retrieval either does nothing or suppresses legitimate low-trust evidence; what works is excluding or capping untrusted content at retrieval, plus ground-truth verification where it exists. AutoMemory's tiers are therefore ahead of practice, but the tiers must act as hard gates/caps, not as score penalties.

### Cited Findings

Attacks (baselines to defend against)
- AgentPoison (arXiv v1 17 July 2024): poisoning "less than 0.1%" of a memory/knowledge base gives an average attack success rate "higher than 80%" on three agents (RAG autonomous driving agent, knowledge QA agent, healthcare EHRAgent), with under 1% drop on benign instructions **[measured]** — [arXiv 2407.12784](https://arxiv.org/abs/2407.12784)
- MINJA (arXiv v1 5 March 2025, v5 revised 12 Feb 2026): attacker needs only query access; "injects malicious records into the memory bank by only interacting with the agent via queries" — [arXiv 2503.03704](https://arxiv.org/abs/2503.03704). Secondary summaries report >95% injection success and ~70% attack success under idealised conditions on GPT-4o-mini, Gemini-2.0-Flash and Llama-3.1-8B; those numbers were not confirmed from the abstract page — [alphaxiv summary of 2601.05504](https://www.alphaxiv.org/abs/2601.05504)
- ICML 2026, "From Untrusted Input to Trusted Memory: A Systematic Study of Memory Poisoning Attacks in LLM Agents": taxonomy of six attack classes and a benchmark (MPBench); agents that write and retrieve memory more aggressively are easier to exploit; existing prompt-injection defenses do not cover memory poisoning **[measured, numbers not retrieved]** — [ICML 2026 virtual page](https://icml.cc/virtual/2026/67964); preprint [arXiv 2603.20357](https://arxiv.org/abs/2603.20357)
- MemoryGraft (arXiv 2512.16962): persistent compromise through poisoned experience retrieval, tested on the MetaGPT multi-agent framework; authors flag shared multi-agent memory pools as an open question — [emergentmind listing](https://www.emergentmind.com/papers/2512.16962)
- EMNLP 2026 Findings paper on query-efficient memory injection includes a multi-agent scenario where several agents share one memory pool — [aclanthology 2026.findings-emnlp.1312](https://aclanthology.org/2026.findings-emnlp.1312.pdf) (full text not retrieved)
- Newer attack classes beyond MINJA: forged reasoning traces (FARMA, [arXiv 2607.05029](https://arxiv.org/pdf/2607.05029)); indirect poisoning via untrusted tool inputs ([arXiv 2607.06595](https://arxiv.org/pdf/2607.06595)); "misattribution gap" paper reports MINJA- and AgentPoison-style entries were all flagged by four classifiers but a separate class it calls SND was missed ([arXiv 2605.22842](https://arxiv.org/html/2605.22842v1))

Measured defenses
- "Utility Under Attack" (Arulnidhi Karunanidhi, arXiv 2608.21230, Aug 2026): poisoning 1.2% of a LongMemEval corpus with plainly worded false assertions (no triggers, no retriever optimisation) cut accuracy from 0.850 to 0.300. A four-stage write-time content screen had recall 0.832 on indirect prompt injection but rejected 0 of 360 poisoned memories and flagged 1.5% of benign text. Provenance-weighted retrieval at the shipped weight was statistically indistinguishable from no defense (p=0.80); a weight strong enough to exclude untrusted content raised accuracy 0.3167→0.7000 on a mixed corpus but, when the answer-bearing evidence itself was untrusted, drove evidence recall to zero and accuracy to 0.0417. Recommendation: bounded occupancy constraints (caps on how many untrusted items may occupy the retrieved set) instead of additive provenance penalties **[measured]** — [arXiv 2608.21230v1](https://arxiv.org/abs/2608.21230v1)
- "Memory Poisoning Attack and Defense on Memory Based LLM-Agents" (arXiv 2601.05504v2, Jan 2026): MINJA on an EHR agent; ASR 62% (GPT-4o-mini) / 52.94% (Llama-3.1-8B) with empty memory, falling to 6.67% / 0% when six relevant prior memories already exist; ASR rises with retrieval k (3→10 memories: 6%→38% on GPT-4o-mini). Their trust-score sanitiser behaved as a "confidence filter not a security filter": on Gemini-2.0-Flash it accepted 82 entries at trust 1.0 of which 54 were poisoned; on GPT-4o-mini it rejected everything, so utility was zero. Authors call for ground-truth verification and decoupling trust from model self-assessment. Single run per model, no variance reported **[measured, weak]** — [arXiv 2601.05504](https://arxiv.org/html/2601.05504)
- SMSR (arXiv 2606.12703) claims a certified defense cutting a query-only attack from 65.3% to 5.3% success (n=150), tested only on its own stack, not replicated **[measured, single source]** — [arXiv 2606.12703](https://arxiv.org/html/2606.12703)
- MemConflict (arXiv 2605.20926, May 2026, Renmin University et al.): benchmark for dynamic, static and conditional memory conflicts across six long-term memory systems; finds a "notable disconnect between answer correctness and underlying memory quality"; longer histories, distractors, implicit queries and larger conflict distance all degrade performance; failures trace to missing supporting memories and poor use of retrieved ones **[measured]** — [arXiv 2605.20926](https://arxiv.org/pdf/2605.20926)

How products label authorship and trust
- Letta shares memory by attaching the same block to several agents; `read_only=True` is the only per-block write restriction; `memory_insert` is append-only and concurrent-safe, `memory_replace` "fails if target string changed", and `blocks.update()` replaces the whole block (so can overwrite a concurrent write) — [Letta shared memory docs](https://docs.letta.com/guides/agents/shared-memory-blocks)
- mem0 scopes by `user_id`, `agent_id`, `run_id`; its security guidance lists timestamps, provenance and audit logs as production recommendations rather than built-in features — [mem0 security best practices](https://mem0.ai/blog/ai-memory-security-best-practices); third-party comparison: "multi-agent shared memory requires custom implementation; it is not native" — [atlan comparison 2026](https://atlan.com/know/best-ai-agent-memory-frameworks-2026/)
- Zep stores provenance as graph relationships between facts and their source episodes in its temporal graph (Graphiti); some provenance bookkeeping lives in separate structures outside the graph — [ZenML LLMOps database entry](https://www.zenml.io/llmops-database/provenance-and-lineage-tracking-in-llm-powered-agent-memory-systems)
- OpenViking (Volcano Engine, AGPLv3, v0.3.22 cited): `viking://user/{user_id}/{memories,resources,skills,peers}` virtual filesystem with L0 abstract / L1 overview / L2 full content; accounts, user isolation and opt-in resource ACLs; root key cannot read or write memories; no provenance or trust fields documented — [OpenViking GitHub](https://github.com/volcengine/OpenViking)
- MCP reference Knowledge Graph Memory Server: entities (name, entityType, observations[]), relations (from, to, relationType, "always stored in active voice"), observations are atomic strings; stored in `memory.jsonl`, written atomically via temp-file rename with a `.lock` file; no timestamps, author or provenance fields — [modelcontextprotocol/servers src/memory](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)
- Research middleware that adds what products lack: Provem (MIT, PyPI) sits in front of Mem0/Zep/own DB and adds provenance and trust tagging, injection quarantine at write, trust-weighted conflict resolution at read, and a SHA-256 hash-chained audit log — [Provem on PyPI](https://pypi.org/project/provem/); Provena adds hash-chained audit with optional HMAC and a BLOCK mode that quarantines entries while still logging them — [Provena GitHub](https://github.com/sm21707/provena); Procheiron's docs state a hash chain gives "tamper evidence, not authenticated provenance" — [Glama listing](https://glama.ai/mcp/servers/iuyvlp8ber); mnemo-core signs writes and reads with Ed25519 or HMAC over content hashes — [docs.rs mnemo-core](https://docs.rs/mnemo-core/0.4.3/src/mnemo_core/provenance.rs.html)

### Inferences
- AutoMemory already has what the papers ask for (author tier, quarantine, ledger). The measured gap is in *how tiers affect retrieval*: a linear score penalty is shown not to work; a hard rule ("agent-claim and untrusted items may fill at most N of k slots, never displace a human pin or verified item on the same key") matches the "bounded occupancy" recommendation.
- 2601.05504 shows a full memory of relevant, trusted items is itself a defense (ASR 62%→6.67%). Seeding projects with verified items and keeping retrieval k small for low tiers is cheap and measured.
- Since agents in AutoMemory can propose but not overwrite a person's items, the remaining poisoning surface is agent-tier and untrusted-tier items being retrieved as if true; the research says content screening of those items will not save you, so mark them visibly in the returned context (tier label in every recall result) and let verification promote them.
- Hash-chained ledgers are now the common pattern in research middleware; AutoMemory's signed operations are stronger than most, but the chain should cover retrieval decisions too (serve/refuse with reason), which Provem does and few others do.

### Gaps
- No paper measures a five-tier scheme like AutoMemory's; the closest (2608.21230) tests two classes (trusted/untrusted).
- Full numeric results of the ICML 2026 MPBench paper, the EMNLP 2026 shared-pool paper and the Feb 2026 preprint on poison spreading between collaborating agents were not retrieved (rate limit); effect sizes for propagation across agents remain unknown.
- No product documentation found that describes a quarantine queue with human review for memory items; only research middleware.

## Key question 2: Conflict handling when several agents or machines write; CRDT and local-first options for SQLite in 2026; is a CRDT worth it?

### Takeaway
For small, mostly-independent records written by few devices, the local-first community itself says CRDTs are a merge primitive, not a sync solution; an append-only op log with ids, hashes and per-field last-writer-wins (what cr-sqlite does per column) plus a human review queue for true conflicts gives nearly all the benefit without a new engine. A full CRDT library is worth it only if you need fine-grained concurrent edits inside one item's text.

### Cited Findings
- Loro's own post "CRDTs are not enough" argues a CRDT is only the merge function; a sync engine must add transport, persistence, versioning and access control — [loro.dev blog](https://loro.dev/blog/crdt-is-not-enough) (page returned 403 on fetch; title and thesis from search)
- Loro 1.0 (2024): new snapshot format roughly twice the old uncompressed size because history and state are encoded separately; shallow snapshots drop old history and "greatly reduce document size"; Rust API `doc.export(ExportMode::shallow_snapshot(&frontiers))` — [Loro 1.0 post](https://loro.dev/blog/v1.0), [shallow snapshot docs](https://loro.dev/docs/advanced/shallow_snapshot)
- Automerge 3.0 (July 2025): memory use down "over 10x" (Moby Dick paste ~700 MB → ~1.3 MB), compressed columnar format used at runtime, file format unchanged from Automerge 2, one document that had not loaded in 17 h loads in 9 s — [automerge.org blog](https://automerge.org/blog/automerge-3/)
- cr-sqlite (MIT, vlcn-io): `SELECT crsql_as_crr('table')` turns a table into a conflict-free replicated relation; per-column CRDT (last-write-wins, counter, fractional index), deletes via causal-length set; changes exchanged through the `crsql_changes` virtual table with `site_id`, `db_version`, `col_version`, `cl`, `seq`; tables need a declared primary key; inserts ~2.5x slower; extension must be loaded on every connection; schema changes need `crsql_begin_alter`/`crsql_commit_alter`; builds need Rust nightly; README warns "main may not be 100% stable" — [cr-sqlite GitHub](https://github.com/vlcn-io/cr-sqlite). A late-2025 reviewer found it "too early-stage for production use" — [MVP Factory comparison](https://mvpfactory.io/blog/crdts-for-offline-first-mobile-sync-automerge-vs-yjs-merge-semantics-and-the/)
- Evolu: SQLite on all platforms, CRDT merging, end-to-end encrypted sync and backup, self-hostable sync server — [Evolu site](https://evolu-git-changeset-release-main-evolu.vercel.app); ElectricSQL is Postgres→client sync (needs a Postgres) — [electric alternatives page](https://electric.ax/docs/sync/reference/alternatives.md); Ditto: no technical details found beyond alternative lists
- Yjs is repeatedly called the most mature JS CRDT with the smallest memory footprint; comparisons are blog-grade — [velt.dev list, July 2026](https://velt.dev/blog/top-crdt-libraries-for-real-time-data-sync), [Smashing Magazine May 2026](https://www.smashingmagazine.com/2026/05/architecture-local-first-web-development/)
- Ink & Switch Keyhive (2024–2026): "convergent capabilities" for local-first data such as Automerge and Git; Beehive = encryption + key management + capabilities; BeeKEM is a TreeKEM variant for E2EE groups of thousands; Beelay is auth-enabled sync over encrypted data; repo last pushed 2026-02-28; Subduction (p2p sync for encrypted CRDTs) is "early preview, not for production" — [Keyhive project page](https://www.inkandswitch.com/project/keyhive/), [Keyhive notebook 06](https://inkandswitch.com/keyhive/notebook/06/), [ecosyste.ms listing](https://awesome.ecosyste.ms/projects/github.com%2Finkandswitch%2Fkeyhive)
- Letta's concurrency model for shared blocks is append-safe inserts, compare-before-replace, and whole-block overwrite for `blocks.update()` — [Letta docs](https://docs.letta.com/guides/agents/shared-memory-blocks)
- MemConflict shows that even single-writer systems mis-rank competing memories; the conflict problem is semantic (which fact is current) as much as syntactic — [arXiv 2605.20926](https://arxiv.org/pdf/2605.20926)

### Inferences
- AutoMemory's signed op log already is an operation-based CRDT in the degenerate case (ops commute when they touch different items/fields). Adding a per-field `(hlc_timestamp, device_id)` version, as cr-sqlite does per column, gives deterministic last-writer-wins on concurrent field edits without importing cr-sqlite's nightly-Rust build and 2.5x insert cost.
- The right place for human review is *semantic* conflicts (two different values for the same key from the same tier, or an agent proposal against a human pin), not byte conflicts. That is a queue, which AutoMemory already has for proposals.
- A text CRDT (Loro/Automerge) only pays off if two agents edit the same long note concurrently; for short memory items, store the whole item per op and let the review queue handle the rare clash.

### Gaps
- No published benchmark of CRDT libraries on small-record workloads over git transport.
- cr-sqlite release cadence and the last tagged version were not visible in the fetched page.

## Key question 3: Sync transports used by local-first developer tools and their trade-offs for small encrypted records

### Takeaway
Git remotes are the dominant developer-tool transport (Obsidian Git, dotfiles, Keybase git) because they are already authenticated and offline-friendly, but every source notes they merge badly and expose metadata unless the client encrypts; relays (Automerge sync server, Yjs providers, Evolu server) merge well but add a service. For small encrypted delta files, git behaves like an append-only object store, which is what AutoMemory uses; the measured cost is manual conflict resolution, which an op log avoids.

### Cited Findings
- Obsidian Git plugin: community reviews say it "does not handle merge conflicts gracefully when you forget to pull before editing" and requires manual resolution; encryption at rest "depends on your repo settings" — [notes-automate review](https://notes-automate.pages.dev/posts/what-is-the-obsidian-git-plugin-for/)
- Obsidian Sync: AES-256-GCM, key derived from the vault password with scrypt and a salt (parameters not published); password is not stored, loss makes the remote vault unusable and recovery is a full re-setup with a new remote vault — [Obsidian Sync security](https://obsidian.md/help/sync/security)
- Community Obsidian plugins offer AES-256-GCM to S3/WebDAV/OneDrive, and a git-backed plugin with optional encryption where "the host only ever stores unreadable data, including file names" — [community.obsidian.md plugin listings](https://community.obsidian.md/plugins/vault-sync-git)
- Keybase encrypted git: the git helper "performs all the crypto while letting git do its thing"; members added later can read; removed members lose access — [Keybase blog](https://keybase.io/blog/encrypted-git-for-everyone)
- Litestream v0.5 (Oct 2025) replica targets: S3, GCS, Azure Blob, NATS JetStream; one replica destination per database; Age encryption was removed in v0.5.0+ — [Fly.io v0.5.0 post](https://fly.io/blog/litestream-v050-is-here/), [Litestream migration guide](https://litestream.io/docs/migration/)
- Automerge 3 positions itself for "offline use, multiple sync servers, and peer-to-peer" — [automerge.org blog](https://automerge.org/blog/automerge-3/); Evolu runs a free hosted sync server and allows self-hosting — [Evolu site](https://evolu-git-changeset-release-main-evolu.vercel.app)
- Keyhive/Beelay and Subduction are the research direction for relay sync of E2EE CRDTs; Subduction is explicitly not production-ready — [Keyhive notebook](https://www.inkandswitch.com/keyhive/notebook/)

### Inferences
- Git's advantages for AutoMemory are real (any private remote, SSH auth, offline, no service); its two weaknesses are: (1) history grows forever (fix: periodic encrypted snapshot + prune old deltas, which Litestream's compaction levels illustrate), and (2) file names and commit metadata leak (fix: opaque names, as the Obsidian git-encryption plugin does).
- A relay is only worth adding as an optional second transport (e.g. a WebDAV/S3 bucket of the same encrypted delta files) rather than a protocol change.

### Gaps
- No quantitative comparison of git vs object store vs relay for many small files; costs are anecdotal.
- Logseq sync internals not researched (rate limit).

## Key question 4: Backup and restore best practice for SQLite-based local tools

### Takeaway
Authoritative guidance: never plain-copy a live WAL database; use the online backup API or `VACUUM INTO` for snapshots, and a continuous page-level replicator (Litestream-style LTX files with hierarchical compaction) for point-in-time recovery. Verification means `PRAGMA integrity_check` **plus** a row-level check and a periodic scripted restore, because a copied WAL database can pass integrity_check yet miss committed rows.

### Cited Findings
- SQLite official backup page: copying with an external tool needs a shared lock for the whole copy and a crash mid-copy can corrupt the backup; the online backup API yields a bit-wise identical snapshot as of start, restarts if another process writes mid-backup (can never finish under frequent writes), but continues if the write comes through the same connection; `VACUUM INTO` creates a vacuumed copy of a live database; `sqlite3_rsync` copies a live database to/from a remote host over SSH — [sqlite.org/backup.html](https://sqlite.org/backup.html)
- `VACUUM INTO` requires SQLite ≥ 3.27.0 and does a full rebuild (benchmark its I/O) — [oneuptime guide 2026](https://oneuptime.com/blog/post/2026-03-02-how-to-back-up-sqlite-databases-on-ubuntu/view)
- In WAL mode committed data may still sit in `-wal`; copying only the main file is safe only when every connection is closed — [oneuptime WAL guide, Sept 2026](https://oneuptime.com/blog/post/2026-09-08-back-up-wal-mode-sqlite-safely/view)
- A copied WAL database "passed PRAGMA integrity_check returned ok yet was missing a committed row"; integrity_check covers structure and constraints, not presence of expected records **[measured, single blog test]** — [thepromptshelf SQLite WAL backup, 2026](https://thepromptshelf.dev/blog/sqlite-wal-backup-before-agent-migrations-2026/)
- Litestream v0.5.0 (3 Oct 2025): LTX files with per-page compression and a trailing index; compaction L1 = 30 s window, L2 = 5 min, L3 = 1 h; restore replays newest→oldest skipping duplicate pages, using "about a dozen files on average"; monotonically increasing TXIDs replace generations; CGO dropped (modernc sqlite); cannot restore v0.3.x WAL files; a user reported a restore-time "transaction not available" error and advised waiting for 0.5.1 — [Fly.io v0.5.0 post](https://fly.io/blog/litestream-v050-is-here/), [Simon Willison 3 Oct 2025](https://simonwillison.net/2025/Oct/3/litestream), [fooqux summary of mtlynch's caution](https://fooqux.com/article/179), [v0.5.1 fix thread](https://community.fly.io/t/litestream-v0-5-1-released/26176)
- Litestream VFS (Dec 2025): open a database at any point in time directly from the replica via pragmas; fails fast on gaps in the LTX sequence; trades disk for network latency — [Fly.io Litestream VFS](https://fly.io/blog/litestream-vfs/), [litestream.io VFS docs](https://litestream.io/how-it-works/vfs/)
- 3-2-1 rule: three copies, two media, one off-site, live data counts as one copy; 3-2-1-1-0 adds an immutable/offline copy and "zero errors after a tested restore" — [safeguard.sh homelab backups](https://safeguard.sh/resources/blog/homelab-backups-explained-3-2-1-restic-borg-offsite-copies-and-restore-tests)
- Restore testing: alert on the age of the last successful restore drill, not just job exit codes; restore to a separate location and check integrity, function, RTO and RPO — [oneuptime automated restore tests, Sept 2026](https://oneuptime.com/blog/post/2026-09-02-automated-backup-restore-tests/markdown), [Duplicati how-to](https://duplicati.com/articles/howto-test-restores-before-disaster-strikes)

### Inferences
- AutoMemory's encrypted op-log remote already provides point-in-time replay if ops are totally ordered per device; a Litestream-style compaction ladder (fold deltas older than a day into an encrypted snapshot, keep hourly/daily/weekly) bounds restore to "about a dozen files" without a new transport.
- Backup via `sqlite3_backup` from the writer's own connection avoids the restart problem on a busy database; a restore command should rebuild into a temp file, run `integrity_check`, compare item counts and ledger head hash against the manifest, then swap atomically.
- Scheduled local snapshots plus the git remote already satisfy 3-2-1 if the user can also export to a second medium (e.g. an encrypted archive on an external disk); provide that export and a "last verified restore" timestamp in `sync_status`.

### Gaps
- No source on what end users of local tools expect from backup UIs (copy count, placement, restore confirmation); only ops guidance.
- Litestream's removal rationale for age encryption not retrieved (403 on migration guide).

## Key question 5: Portability and open formats for agent memory

### Takeaway
There is no adopted interchange format for agent memory. Letta's `.af` is the most complete agent-state file but omits archival passages and has no format version; mem0 export is schema-shaped summaries from a hosted API; MCP memory is a JSONL graph without timestamps; MIF is a tiny community proposal. Agent Skills (SKILL.md) and AGENTS.md are the only portable conventions with real adoption, and they are for instructions, not memories. A lossless AutoMemory export should therefore be its own documented JSONL op log plus a Markdown/YAML-frontmatter rendering for humans and other tools.

### Cited Findings
- Letta Agent File `.af` (Apache-2.0): contains model config, full message history with `in_context` flag, system prompt, memory blocks, tool rules, environment variables, tool definitions with source and JSON schema; secrets exported as `null`; passages (archival memory) not supported (roadmap); no format version field; roadmap includes migration between schema changes, multi-agent `.af`, converters between frameworks; schema lives in Letta's Pydantic code, not a standalone JSON Schema — [letta-ai/agent-file README](https://raw.githubusercontent.com/letta-ai/agent-file/main/README.md); export endpoint `GET /v1/agents/{id}/export`, import `POST /v1/agents/import`, option to exclude messages — [Letta docs](https://docs.letta.com/guides/agents/agent-file)
- mem0 memory export (hosted platform): you POST a JSON/Pydantic schema plus optional `export_instructions`; filters `user_id`, `agent_id`, `run_id`, `created_at` ranges; output is structured data matching the schema (example is a profile object, not raw records); asynchronous; needs export-permissioned key; no import and no history/provenance documented — [mem0 memory export docs](https://docs.mem0.ai/platform/features/memory-export.md). Third-party migrations (Supermemory, Cognee) loop over a `memories` array with `id, content, user_id, created_at, metadata` — [Supermemory migration](https://supermemory.ai/docs/migration/from-mem0.md), [Cognee migrate](https://docs.cognee.ai/examples/migrate-memory-systems.md)
- MCP reference memory server: JSONL knowledge graph (entities, relations, observations), no timestamps or authorship, `memory://knowledge-graph` resource as `application/json` — [modelcontextprotocol/servers memory](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)
- OpenViking: memories are plain Markdown files under `viking://user/{id}/memories/` that users "can inspect, edit, and merge"; no dedicated export/import/backup commands; hosted SaaS promises migration tooling — [OpenViking GitHub](https://github.com/volcengine/OpenViking)
- MIF (Memory Interchange Format) v2.0, Apache-2.0, 2026: JSON envelope with three required fields (`id`, `content`, `created_at`), optional type, tags, entity refs, embeddings, knowledge graph, vendor extensions, privacy markers; adapters for mem0, CrewAI, LangMem, generic JSON and Markdown with YAML frontmatter; 5 stars, 0 forks; an MCP SEP (#2342) proposal exists — [mif-spec GitHub](https://github.com/varun29ankus/mif-spec)
- Agent Skills spec (agentskills.io, published by Anthropic Dec 2025): folder with required `SKILL.md`; frontmatter `name` (≤64 chars, lowercase/digits/hyphens, must match directory), `description` (≤1024), optional `license`, `compatibility` (≤500), `metadata` (string map), experimental `allowed-tools`; progressive disclosure (metadata ~100 tokens, body <5000 tokens recommended, ≤500 lines); `skills-ref validate` — [agentskills.io/specification](https://agentskills.io/specification). Adoption reported as 30+ tools (Apr 2026) to 41 platforms; skills.sh registry >90,000 listings by July 2026; a July 2026 compatibility test reportedly found a "significant portability gap" (not verified) — [noqta.tn](https://www.noqta.tn/en/news/skill-md-open-standard-30-ai-coding-tools-adoption-2026), [danielvaughan.com](https://codex.danielvaughan.com/2026/05/05/agent-skills-open-standard-portable-skills-codex-cli-cross-agent/)
- AGENTS.md is stewarded alongside MCP by the Agentic AI Foundation per one source; a single low-quality source claims Linux Foundation governance of Skills in May 2026 — [productbuilder.net](https://productbuilder.net/learn/agent-skills)

### Inferences
- A lossless export must contain, per item: stable id, content, type, scope (project/global), tier, author identity (person/device/agent), created/updated HLC timestamps, signature, supersedes/superseded-by links, verification evidence (test id or code hash), quarantine/review state, and the ledger entries that produced it. None of the surveyed formats carries tier, signature or verification, so AutoMemory should publish its own JSON Schema and version it in every file (the one thing `.af` lacks).
- A second, lossy, human-readable export as Markdown with YAML frontmatter (MIF's Markdown adapter, OpenViking's Markdown memories and Obsidian all read this) gives interoperability for free; `.af` import/export can be a converter limited to memory blocks.
- Agent Skills `metadata` map is the sanctioned place to carry AutoMemory ids/tiers if memories are ever rendered as skills.

### Gaps
- No evidence of any two vendors interchanging memories in production; MIF adoption is near zero.
- Letta `.af` date and versioning policy not stated in the README.

## Key question 6: Per-person identity in a team vault: keys per person vs per device, rotation and revocation

### Takeaway
The proven pattern (Keybase, its successor FOKS) is device keys that never rotate plus a per-user key (PUK) whose seed is boxed for each active device, re-generated with a new generation number on every device revocation, with team keys rotating lazily when any member's PUK rolls; a "box auditor" catches missed rotations. SOPS/age show the cheap version: wrap one data key per recipient and re-wrap (`updatekeys`) when the recipient set changes, rotating the data key only on compromise.

### Cited Findings
- Keybase PUK: each generation starts from a random 32-byte seed; HMAC-SHA256 with distinct labels derives an EdDSA signing key, a Curve25519 DH key and a SecretBox key; seed is encrypted for each active device and paper key; adding a device = encrypt the existing seed for it ("instantaneous"); revoking a device = new seed, new generation (+1), boxed for remaining devices, written to the sigchain with a reverse signature, previous seed encrypted under the new generation's key; team keys must rotate when a member's PUK rolls, "lazily, before the next write"; pitfall: a user can have device keys but no PUK — [Keybase PUK doc](https://book.keybase.io/docs/teams/puk)
- Keybase: device long-term keys never rotate; per-user and per-team keys rotate on device revocation or member removal; a stolen laptop can still read team data if the team key was not rotated, hence the Team Box Auditor — [Keybase security](https://book.keybase.io/security), [Team Box Auditor](https://book.keybase.io/docs/teams/box-auditor)
- FOKS (Federated Open Key Service, 2025): when a device or user is revoked, "all keys further up the tree rotate automatically" — [FOKS whitepaper](https://css.csail.mit.edu/6.566/2026/readings/foks-whitepaper.pdf), [FOKS announcement](https://blog.foks.pub/posts/introducing/)
- SOPS with age: data key wrapped separately for each recipient; `sops updatekeys` re-wraps only the data key for a new recipient list; `sops rotate` generates a fresh data key and re-encrypts all values; on compromise, destroy the old private key on every operator machine; re-keying never revokes access to copies already in git history — [rrchnm SOPS rotation runbook](https://docs.rrchnm.org/runbooks/sops-key-rotation/), [oneuptime SOPS rotation, Mar 2026](https://oneuptime.com/blog/post/2026-03-13-how-to-rotate-sops-age-keys-without-re-encrypting-all-files-in-flux/view)
- Obsidian Sync: one vault password → scrypt-derived AES-256-GCM key; no per-device keys; loss of password = loss of remote vault — [Obsidian Sync security](https://obsidian.md/help/sync/security)
- Ink & Switch Beehive/BeeKEM: TreeKEM variant for local-first E2EE groups; capabilities for authorisation — [Keyhive project](https://www.inkandswitch.com/project/keyhive/)
- Pass (password-store) mailing list: the classic gpg-recipient model cannot expire a departed user's access to already-encrypted history — [password-store list, Feb 2019](https://lists.zx2c4.com/pipermail/password-store/2019-February/003589.html)

### Inferences
- AutoMemory's BIP-39 phrase is an Obsidian-style single vault secret: fine for one person, wrong for a team. The Keybase shape maps directly: per-device Ed25519/X25519 keys (never rotate, sign ops), a per-person key boxed to each device, and a per-vault content key boxed to each person; revoking a device bumps the person generation and re-boxes; removing a person rotates the vault key before the next write.
- Ops should be signed by the device key and carry (person id, device id, generation) so provenance survives rotation; forward secrecy for old deltas is not achievable in git (history remains readable to anyone who held the old key), so document that revocation protects future writes only, as SOPS guides do.
- A box-auditor equivalent (`sync_status` warning when any active device lacks a box for the current generation, or when a revoked device still has a box for the vault key) is cheap and catches the Keybase failure mode.

### Gaps
- 1Password's vault key model and Keybase-style revocation in other consumer tools were not researched (rate limit).
- FOKS whitepaper details (exact tree and rotation cost) were not read.

## Key question 7: Secret hygiene: detection and redaction before storage with offline tools

### Takeaway
Two mature, offline, permissively licensed rule sets exist: gitleaks (MIT, TOML rules, composite rules since v8.28.0, now "feature complete" with security patches only as the maintainer moves to Betterleaks) and Yelp detect-secrets (Apache-2.0, 24 provider detectors plus entropy and keyword plugins, network verification optional via `--no-verify`). The practical move is to vendor gitleaks' TOML rules into a write-time scan that quarantines or redacts matches, and to keep an allowlist file so false positives can be accepted once.

### Cited Findings
- gitleaks: MIT; `.gitleaks.toml` with `[[rules]]`, `[extend]` to inherit defaults, per-rule and global `[[allowlists]]` (commits, paths, regexes, stopwords, AND/OR), inline `gitleaks:allow`, `.gitleaksignore` fingerprints; commands `git`, `dir`, `stdin` (`detect`/`protect` deprecated since v8.19.0); composite `[[rules.required]]` with `withinLines`/`withinColumns` since v8.28.0; optional recursive percent/hex/base64 decoding via `--max-decode-depth`; README states "Gitleaks is feature complete" and future releases are security patches only, focus moving to Betterleaks — [gitleaks GitHub](https://github.com/gitleaks/gitleaks). Secondary sources cite 140+ built-in rules — [appsecsanta](https://appsecsanta.com/gitleaks)
- detect-secrets (Yelp, Apache-2.0, v1.5.0): regex plugins (AWS, Azure, GitHub, GitLab, JWT, OpenAI, PrivateKey, Slack, Stripe, Twilio, etc.), `Base64HighEntropyString`/`HexHighEntropyString`, `KeywordDetector`; baseline file separates known from new secrets; `audit` labels true/false positives; `--no-verify` disables network verification; inline `pragma: allowlist secret`; does not catch multi-line secrets — [detect-secrets GitHub](https://github.com/Yelp/detect-secrets)
- TruffleHog's precision advantage comes from live verification, which needs network; gitleaks wins on recall for custom formats with tuned rules — [dev.to benchmark (self-published, unverified)](https://dev.to/johalputt/benchmark-gitleaks-8-vs-trufflehog-3-vs-spectral-2-for-secret-detection-accuracy-in-git-repos-36l9)
- Letta `.af` nulls secrets on export; MIF carries optional privacy markers for PII detection and redaction — [agent-file README](https://raw.githubusercontent.com/letta-ai/agent-file/main/README.md), [mif-spec](https://github.com/varun29ankus/mif-spec)

### Inferences
- A Rust local-first tool can embed gitleaks' default TOML (MIT) and evaluate it with the `regex` crate at write time; entropy checks from detect-secrets are a few lines. Redact to `[REDACTED:<rule-id>:<sha256 prefix>]` so the ledger still proves what was removed without storing it.
- Because gitleaks is frozen, pin the rule file version in the export schema and note Betterleaks as the successor to track.

### Gaps
- No measured false-positive rates for secret scanners on prose memory items (all benchmarks are on code repositories).

## Concrete gaps and recommendations for AutoMemory (local-first, optional private remote)

1. Retrieval policy, not scoring (measured): replace any additive tier weight with hard caps per tier in the retrieved set and never let agent-claim/untrusted items displace a human pin or verified item on the same key; label tier in every returned item (2608.21230, 2601.05504).
2. Ground-truth promotion: the only defense both 2026 papers endorse is verification against something outside the model; keep "verified by test or code hash" as the only path from agent claim to fact, and record the evidence hash in the item.
3. Keep retrieval k small for low tiers and seed projects with verified items; measured ASR fell from 62% to under 7% when relevant trusted memories were present.
4. Ledger covers reads: log serve/refuse decisions with reason and tier (Provem pattern) so poisoning can be traced to the retrieval that used it.
5. Conflicts: add per-field `(HLC, device_id)` versions to ops for deterministic LWW across machines; route only semantic clashes (same key, same tier, different value; or agent proposal vs human item) to the existing review queue. Do not adopt cr-sqlite or a text CRDT unless concurrent in-item text editing becomes a feature.
6. Remote growth: Litestream-style compaction ladder (fold deltas older than a day into encrypted snapshots; keep hourly/daily/weekly) so a restore needs about a dozen files; opaque file names in the remote.
7. Backup: snapshot with the online backup API from the writer connection or `VACUUM INTO`; verify with `integrity_check` + item count + ledger head hash; expose "last verified restore" in `sync_status`; offer an encrypted archive export for a second medium (3-2-1).
8. Portability: publish a versioned JSON Schema for the op-log export (id, content, type, scope, tier, author person/device/agent, HLC timestamps, signature, supersedes links, verification evidence, review state, ledger refs); add a lossy Markdown+YAML-frontmatter export (reads in Obsidian, OpenViking, MIF adapters); an `.af` converter limited to memory blocks.
9. Team identity: move from one BIP-39 vault secret to device keys (never rotate, sign ops) + per-person key boxed per device with generation numbers + vault content key boxed per person; rotate vault key before the next write after a removal; add a box-auditor check; document that revocation protects future deltas only.
10. Secret hygiene: embed gitleaks' MIT TOML rules plus entropy/keyword checks at write time; redact with rule id and hash; per-vault allowlist; pin the rule-set version.

Skipped or not checked: full text of the ICML 2026 MPBench paper, the EMNLP 2026 shared-pool paper and the Feb 2026 propagation preprint (rate limit), Logseq and 1Password internals, Litestream's age-removal rationale. Risk: several poisoning-defense numbers come from single-author preprints with one run and no variance; treat them as directional until replicated.
