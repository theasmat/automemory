# Verified, sparse memory beats bigger memory

**Bottom line: AutoMemory's design is already on the right side of every measured result in 2025–2026 agent-memory research, and the way to be measurably better than mem0, claude-mem, Letta/Zep and OpenViking is not to add their machinery but to tighten what AutoMemory already has and then publish numbers.** The evidence says four things. First, no commercial memory system beats a no-memory or plain-BM25 baseline on honest benchmarks: on MemoryAgentBench BM25 RAG scores 60.5 on accurate retrieval against Mem0's 32.6 and Zep's 37.5, and on the coding-specific VibeMemBench 11 of 12 memory-system pairings land at or below the no-memory baseline ([MemoryAgentBench](https://arxiv.org/html/2507.05257v4); [VibeMemBench](https://arxiv.org/html/2609.23570v1)). Second, what does help coding agents is a small set of non-inferable, verified records; LLM-generated context files cost 20% more and gain nothing, while 69% of memory failures are "form degradation" from instruction pollution and raw logs ([Gloaguen et al.](https://arxiv.org/html/2602.11988v3); [VibeMemBench](https://arxiv.org/html/2609.23570v1)). Third, the only poisoning defenses with measured effect are provenance caps and ground-truth verification, not content screening, and trust tiers must act as hard occupancy caps rather than score penalties ([Utility Under Attack](https://arxiv.org/abs/2608.21230v1); [A-MemGuard](https://proceedings.mlr.press/v306/wei26ac.html)). Fourth, time decay as a score multiplier has two independent negative ablations ([MEMTIER](https://arxiv.org/html/2605.03675v3); [vstash](https://arxiv.org/html/2604.15484v1)), which puts AutoMemory's current BM25 × decay × confidence formula under suspicion. The competitive gaps that matter are an offline consolidation pass, bi-temporal supersession, key expansion at index time, a versioned export format, team-grade key management and, above all, a published benchmark on coding tasks. The plan at the end orders fourteen changes by evidence strength and effort, each with the measurement that would confirm it.

## Competitors differ in write path, not in retrieval quality

The 2026 market split three ways: LLM-extraction cloud APIs (Mem0, Zep/Graphiti, Supermemory, Hindsight), file-shaped memory inside the harness (Claude Code auto memory, Letta Code's git-backed memory, OpenViking's `viking://` filesystem, Copilot memory), and local SQLite+FTS5 sidecars for coding agents (claude-mem, engram). AutoMemory sits in the third group but carries features none of its peers have: five trust tiers, verification of notes against file and symbol hashes, automatic file locks, encrypted git-vault sync and built-in backup/restore. No competitor README or doc read for this report mentions file locking at all, and none exposes a per-item trust tier or quarantine ([Copilot memory docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory); [claude-mem README](https://github.com/thedotmack/claude-mem)).

The most instructive competitor move is Mem0's reversal. Its ECAI 2025 paper describes an LLM that picks ADD/UPDATE/DELETE/NOOP for every extracted fact, and even on its own benchmark full context (72.90) beat Mem0 (66.88); the win was latency and tokens, not accuracy ([Mem0 paper](https://arxiv.org/html/2504.19413v1)). Users reported that "when the model gets a distinction wrong, it quietly issues a DELETE" ([dev.to](https://dev.to/mukesh_13/mem0-auto-resolves-memory-conflicts-for-you-until-it-silently-deletes-one-you-still-need-4f4m)), and in April 2026 SDK v2.0 switched to **"ADD-only extraction: memories accumulate and nothing is overwritten or deleted"**, with search-time decay (a 0.3x–1.5x ranking bias that reorders but never filters) and explicit `expiration_date` added over the following months ([Mem0 changelog](https://docs.mem0.ai/changelog/highlights)). The market leader abandoned LLM-driven deletion for deterministic append-plus-decay, which is where AutoMemory already stands. Mem0 also shipped two CVEs in May 2026 for unauthenticated `DELETE /memories` endpoints and disclosed 18 SQL injection points in its PGVector backend ([Mend CVE-2026-31241](https://www.mend.io/vulnerability-database/CVE-2026-31241/)), and sunset its local-first OpenMemory MCP server, so the still-maintained local MCP memory niche is thinner than it looks.

claude-mem, at roughly **116K stars**, is the volume leader for coding agents, and its architecture is the opposite of AutoMemory's: a second LLM "observer" compresses every tool call into observations, which needs Bun, uv and a paid or metered model. Its own README concedes the token-savings ratio "is not a measured recall or end-to-end saving", and one user measured 1.485M tokens per session against 20K for a transcript-grep alternative ([claude-mem README](https://github.com/thedotmack/claude-mem); [claude-historian comparison](https://glama.ai/mcp/servers/@Vvkmnn/claude-historian/blob/5523c7a4febebd9cb3e54990eb6bc693ee206aa5/COMPARISON.md)). What it does well is progressive disclosure: a `search` index at 50–100 tokens per row, then `timeline`, then `get_observations` at 500–1,000 tokens, which cut session-start context by about 87% when it replaced a 50-observation push ([claude-mem architecture evolution](https://docs.claude-mem.ai/architecture-evolution)). engram, a single Go binary with FTS5 only, mirrors that triple and adds "conflict surfacing" tools (`mem_judge`, `mem_compare`) and a refusal to switch projects silently ([engram README](https://cdn.jsdelivr.net/gh/Gentleman-Programming/engram@main/README.md)).

Zep/Graphiti contributes the one schema idea worth copying: every fact edge carries valid-at and invalid-at timestamps and **contradicted facts are invalidated, never deleted** ([aktagon summary](https://signals.aktagon.com/articles/2026/07/zep-a-temporal-knowledge-graph-architecture-for-agent-memory/)). Its weakness is that no accuracy number exists for that invalidation, the self-hosted Zep edition is deprecated, and the hosted tier starts around $104 a month ([rywalker Zep](https://rywalker.com/research/zep)). Letta's contribution is sleep-time compute, an idle-time agent that rewrites core memory and reportedly cuts test-time compute about 5× for equal accuracy ([Letta/UC Berkeley](https://arxiv.org/html/2504.13171v1)), plus FrontierMemory, the first benchmark that scores memory by how much it helps a fresh agent, though it is only 15 tasks with ±6.7 pp per error ([The New Stack](https://thenewstack.io/letta-frontiermemory-agent-harness-benchmark/)). OpenViking brings the L0/L1/L2 tiered loading (one-sentence abstract, overview, full file) and directory-scoped search, but its core is AGPL-3.0, it needs an embedding model and a VLM, and its 24→82% LoCoMo numbers are vendor-run on Doubao models ([OpenViking README](https://github.com/volcengine/OpenViking)). Finally GitHub Copilot memory, GA since October 2026, is the closest analogue to hash verification: repository facts cite supporting code, citations are re-checked against the current branch before use ("a judgment, not a guarantee"), validated memories are upvoted, wrong ones downvoted, and unreinforced facts expire after 90 days ([Copilot memory docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). AutoMemory's hash check is stronger because it is deterministic; Copilot's vote-and-expiry layer on top is what AutoMemory lacks.

The table below collapses the gap analysis to what is both missing and evidence-backed.

## Honest benchmarks say BM25 wins and memory often loses

Any vendor LoCoMo or LongMemEval score above about 90 should be read as a harness artifact. The LoCoMo judge accepts roughly 63% of intentionally wrong answers and about 6.4% of its ground truth is wrong, so the honest ceiling is 93–94%; the same system scores anywhere from 38% to 92% depending on harness, and Gemini 2.5 Flash reading the raw transcript with no memory system at all scores 72.8% ([Penfield Labs](https://dev.to/penfieldlabs/proposal-a-real-benchmark-for-long-term-ai-memory-systems-57p5); [memoryplugin field guide](https://www.memoryplugin.com/wiki/evaluating.html)). The only third-party reruns found put Mem0 cloud at 56.0 on LongMemEval against its reported 94.4 and Zep at 63.8 on LoCoMo against its claimed 94.7 ([dev.to benchmark write-up](https://dev.to/everest_an/-i-benchmarked-ai-agent-memory-in-2026-and-the-numbers-tell-a-different-story-than-the-marketing-2ae4)). The harder, newer benchmarks are consistent with each other: on MemoryAgentBench **BM25 RAG beats every embedding RAG and every memory product on accurate retrieval (60.5 vs Mem0 32.6, Zep 37.5)**, and on selective forgetting with multi-hop updates every system scores 5.0 or below ([MemoryAgentBench](https://arxiv.org/html/2507.05257v4)).

For coding specifically the picture is sharper and less flattering. SWE-ContextBench (Claude Sonnet 4.5, 99 Lite tasks) found the baseline at 26.26%, Mem0 at 24.24% (below baseline), autonomous summary retrieval at 22.22% (below baseline, because irrelevant summaries mislead), and only an oracle summary reaching 34.34% ([SWE-ContextBench](https://arxiv.org/html/2602.08316v3)). VibeMemBench, built from 111 coding targets across 90 repositories, found the best existing system at or below no-memory in 11 of 12 pairings, and even an oracle of "frozen verified experience" added only 0.0 to 4.5 pp with every confidence interval crossing zero. Its failure attribution is the single most useful datum for AutoMemory: **69.3% of failing pairings were form degradation**, where relevant history reached the solver but was buried or dropped, split into instruction pollution (40%), over-generalised fix patterns (18%) and tool or shell noise (10%); coverage misses were 16% and ranking misses only 1.3% ([VibeMemBench](https://arxiv.org/html/2609.23570v1)). Retrieval ranking is nearly solved; what the agent is handed, and in what form, is the problem.

The same message comes from the AGENTS.md study presented at ICLR 2026. Across Claude Code, Codex and Qwen Code on SWE-bench Lite and CTXbench, LLM-generated context files changed resolution by −0.5 and −2 pp (not significant) while raising cost 20–23% and adding 2.5–3.9 steps per task; developer-written files gained +2.4 pp (p=0.21) and beat LLM-generated ones by about 7 pp, the only significant result ([Gloaguen et al.](https://arxiv.org/html/2602.11988v3)). Agents follow what they are given (`uv` used 1.6 times per instance when mentioned versus under 0.01 otherwise), so a file that adds checks adds cost, and repository overviews, present in 95–100% of generated files, "did not reduce the steps needed to reach the relevant files". A follow-up with 288 runs found the real AGENTS.md "never turned a near-miss into a pass" ([Khatri](https://arxiv.org/abs/2607.27250)). The one case where generated context helped (+2.7 pp) was when all other repository documentation was removed, which is why anecdotes of gains on under-documented repos survive.

Where memory does pay is when it holds what the environment cannot reveal. Anthropic's CL-Bench database task moved Opus 4.7 from 0.383 to 0.700 mean reward with memory, and a cross-document legal set went from 73% with search alone to 87% with a curated wiki plus search, with no gain when facts sat in one document; the model that gained most stored strategies, plans and tested rules and skipped screen-readable state ([Anthropic](https://www.anthropic.com/research/components-of-agent-memory)). The same study measured the cost of volume (413 indiscriminate files earned one badge where ten curated files earned four) and of rigid salience rules ("record only failures" cut memory gains by up to 0.234), and showed that one page per entity with verbatim terms kept 57 of 57 contract facts where a shared table kept 41 of 57, with concurrent writers overwriting each other's facts. Put together with the AGENTS.md result, the rule for AutoMemory is a write policy: decisions, failed approaches, tested rules, cross-file constraints and non-standard practices belong in memory; anything derivable from the repository, including the "project overview" record type, does not, and Claude Code's own auto memory already follows this by skipping "architecture, file paths, or debugging fixes" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)).

On retrieval mechanics the ablations are unusually clear. LongMemEval, peer-reviewed at ICLR 2025, found fact-augmented key expansion worth +9.4% recall@k and +5.4% QA accuracy, and time-aware indexing plus query expansion worth +6.8–11.3% recall on temporal questions ([LongMemEval](https://arxiv.org/html/2410.10813v2)); both are deterministic index-time operations. MEMTIER's ablation on LongMemEval-S measured BM25 at 0.360 in 25.7 ms, dense at 0.380 in 92.6 ms and hybrid RRF at 0.390 in 96.7 ms, but hybrid *reduced* knowledge-update accuracy from 0.500 to 0.375 because dense similarity surfaces superseded facts, and **removing time decay, cognitive weight or tier boost each raised accuracy by 0.012–0.014** ([MEMTIER](https://arxiv.org/html/2605.03675v3)). vstash, a SQLite+FTS5+sqlite-vec system close to AutoMemory's shape, found that a frequency-plus-decay reranker lowered NDCG@10 in every configuration (−1.6% adaptive, −9.0% fixed), that cross-encoder reranking hurt by 0.3–3.1%, and that RRF weights set per query from mean IDF beat fixed weights on all five BEIR sets ([vstash](https://arxiv.org/html/2604.15484v1)). Graph traversal bought Mem0 about 2 points at twice the tokens and three times the search latency ([Mem0 paper](https://arxiv.org/html/2504.19413v1)). The implication for a 5 ms hook is to keep FTS5 as the primary ranker, expand keys at index time, make time decay a filter on volatile record types rather than a multiplier, and treat vectors, reranking and graphs as optional at best.

Staleness and contradiction remain unsolved everywhere, which is AutoMemory's opening. No paper reports precision or recall for detecting that a stored fact is no longer true; Graphiti's invalidation has no accuracy numbers, and the Agent Memory Atlas notes its eval utilities "do not establish that temporal extraction or entity resolution is objectively correct" ([Agent Memory Atlas](https://neoneye.github.io/agent-memory-atlas/systems/graphiti/)). MemConflict found a "notable disconnect between answer correctness and underlying memory quality" across six systems ([MemConflict](https://arxiv.org/pdf/2605.20926)). A field study of stale instruction files is the most direct evidence of the damage: across 320 runs **90.1% of convention choices followed the stale file and 4.2% followed the code**; Claude Code noticed the conflict in 79 of 80 runs and still obeyed the file, and Codex rewrote working code in 20 of 80 runs, breaking tests in 17. One sentence giving existing code precedence raised code-following to 91.4% and the test pass rate from 89.4% to 100% ([Xu & Wu](https://arxiv.org/abs/2610.30571)). The single wrong landmark note in Anthropic's study made the agent loop three times and never reach the goal until an offline pass corrected it ([Anthropic](https://www.anthropic.com/research/components-of-agent-memory)). Verification against ground truth, which is what a code-hash check is, is the one staleness approach with a measured positive effect, and AutoMemory is the only local tool that has it.

## Push a small index, pull the body, and let hooks write

Every major agent now has two layers: a human-written instruction file loaded every session (CLAUDE.md, AGENTS.md, `.cursor/rules`, `copilot-instructions.md`, GEMINI.md) and an agent-written memory layer ranked below it. Claude Code loads only the first 200 lines or 25 KB of its memory index and reads topic files on demand; its docs say "target under 200 lines" because longer files "reduce adherence", that `@path` imports do not reduce context cost, and that a SessionStart hook printing AGENTS.md "adds a second copy to the context" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Codex keeps memories off by default, injects them into the system prompt after the AGENTS.md chain, excludes sessions that used MCP or web search from memory generation (`disable_on_external_context`), and tells teams that "required team guidance should go in AGENTS.md" while memories are "a helpful recall layer" ([Codex memories docs](https://learn.chatgpt.com/docs/customization/memories?surface=app)). Cursor removed Memories entirely in November 2025 and kept only Rules, and users still reported ghost memories being injected afterwards ([Cursor forum](https://forum.cursor.com/t/ghost-user-rules-still-injected-in-agent-context-empty-in-settings-user-tab-not-in-aicontext-personalcontext-logout-login-did-not-fix/164709)). A shared-memory product therefore fits best by writing a short managed block into layer one, exposing recall through MCP and skills, and never trying to be every tool's native memory at once.

The token numbers favour "push the index, pull the body". claude-mem went from about 8,500 tokens for 50 pushed observations to about 800 for an index plus two or three fetched items ([claude-mem](https://docs.claude-mem.ai/architecture-evolution)); mcp-memory-service cut an eight-memory session start from 3,600 to 900 tokens by moving from MCP tool calls to direct code execution ([mcp-memory-service](https://glama.ai/mcp/servers/@doobidoo/mcp-memory-service/blob/0a9494ce57e3cd46d70176bc5527b2f566ea64b4/docs/hooks/phase2-code-execution-migration.md)); the Agent Skills standard loads only name and description at startup and the body on activation ([agentskills.io](https://agentskills.io/)). Pure pull fails because agents do not know to ask; pure push fails on cost and on authority, since system-prompt placement "gives memories high apparent authority" and over-personalisation was measured at 26–61% relative drops across six memory methods in OP-Bench ([Vaughan, citing OP-Bench](https://codex.danielvaughan.com/2026/06/12/codex-cli-memory-over-personalisation-sycophancy-risk-configuration-defence/)). A bare path reference is a "blind reference" that agents often ignore; the configuration-smells study of 100 repositories found 42% with context bloat over 200 lines, 24% whose `/init` output was never edited, and 16% with confirmed conflicting instructions ([dos Santos et al.](https://arxiv.org/html/2606.15828)). The managed block AutoMemory writes should name what exists and when to read it, stay under roughly 80–100 lines, and carry the one-sentence precedence rule that measured 4.2%→91.4% ([Xu & Wu](https://arxiv.org/abs/2610.30571)).

Writes belong in hooks, not in agent discipline. Hook-driven automatic writes cost no tokens, where voluntary MCP store calls cost 20–50 tokens each and, more importantly, are the main poisoning vector ([Vaughan](https://codex.danielvaughan.com/2026/07/03/event-sourced-memory-layers-coding-agents-projectmem-esaa-codex-cli-pretooluse-governance/)). Cisco's April 2026 proof of concept chained an npm `postinstall` into a `UserPromptSubmit` hook that overwrote `MEMORY.md` across every project and framed "hardcode the API key" as a mandatory constraint; Anthropic's response in v2.1.50 removed user memories from the system prompt ([Cisco](https://blogs.cisco.com/ai/identifying-and-remediating-a-persistent-memory-compromise-in-claude-code)), and OWASP added memory poisoning to its 2026 Agentic Top 10 as ASI06. The practical consequence for AutoMemory is that the hook write path must not be modifiable by an installer script, memory must be project-scoped by default (Codex's global consolidation carried a Jest preference into a Go repository), every preference should carry a reason, a scope and a date, and secrets must be scanned before storage because Claude Code, Cursor and Codex all "move secrets through runtime memory, bypassing the artifact layer" ([knostic.ai](https://www.knostic.ai/blog/ai-coding-assistants-leaking-secrets)).

## Local retrieval can improve without a service or an LLM

The cheapest quality step is the FTS5 tokenizer. `porter unicode61 remove_diacritics 2 tokenchars '-_'` gives English stemming, keeps identifiers like `foo_bar` and `t39-phase1` whole, and costs nothing at query time; it needs a one-off FTS rebuild. FTS5 also supports prefix queries, `NEAR`, per-column `bm25()` weights, a trigram tokenizer for substring and typo tolerance, and query-time synonym expansion, but has no built-in spelling correction ([SQLite FTS5](https://www.sqlite.org/fts5.html)). A trigram shadow table used only as a fallback when the stemmed query returns fewer than k hits gives identifier substring matching without taxing the common path. Key expansion, the best-evidenced lift in the literature (+5–11 pp on LongMemEval), means indexing dates, file paths, symbol names and resolved synonyms as extra columns per record, which is a write-time Rust job with no model ([LongMemEval](https://arxiv.org/html/2410.10813v2)).

If vectors are wanted, only one class fits a 5 ms hook. Model2Vec "potion" static embeddings are MIT, pure Rust via `model2vec-rs`, load in 15 ms, embed about 671K texts per second on one core and reach 94.66% of all-MiniLM-L6-v2 on MTEB with the 32M model; a retrieval-tuned `potion-retrieval-32M` exists and the model can be embedded in the binary with `from_bytes` ([model2vec-rs README](https://docs.rs/crate/model2vec-rs/latest/source/README.md); [potion-base-32M](https://huggingface.co/minishlab/potion-base-32M)). Small transformers such as bge-small (MTEB retrieval 51.7), arctic-embed-xs (50.15) or EmbeddingGemma-300M (61.15 multilingual, the best sub-500M model) are better but need ONNX Runtime or candle, which adds tens of megabytes or a shared library and has no measured sub-5 ms CPU batch-1 latency; they belong in a background index pass if anywhere ([arctic-embed-xs card](https://huggingface.co/Snowflake/snowflake-arctic-embed-xs); [EmbeddingGemma](https://arxiv.org/abs/2509.20354v3); [fastembed README](https://docs.rs/crate/fastembed/latest/source/README.md)). At AutoMemory's scale brute force is the right store: sqlite-vec scans 100,000 × 384 f32 vectors in 67.8 ms on an M1 Pro and scales linearly, so 10K is about 7 ms and int8 quantisation cuts that 3–17× with recall@20 of 1.0 in one vendor test ([Bambini](https://marcobambini.substack.com/p/the-state-of-vector-search-in-sqlite)). A plain int8 BLOB column scanned by auto-vectorised Rust needs no extension and no HNSW, which pays off only above roughly 100K notes.

Fusion should start as RRF and stop there until labels exist. Elastic measured RRF at +18% average nDCG@10 over BM25 on BEIR and a per-dataset tuned linear blend at +24%, but tuning needed about 40–300 labelled queries per corpus and the optimal weight is model-specific ([Elastic](https://www.elastic.co/search-labs/blog/improving-information-retrieval-elastic-stack-hybrid)). vstash's IDF-adaptive RRF weights are the one measured improvement on fixed RRF that needs no labels ([vstash](https://arxiv.org/html/2604.15484v1)). Cross-encoder rerankers cost 50–200 ms on CPU (a BGE reranker measured 197 ms median), "small lexical corpora with short queries often don't need reranking", and vstash's result was negative, so a MiniLM reranker belongs only behind an explicit `recall --deep` flag ([arXiv 2609.18672](https://arxiv.org/pdf/2609.18672); [dev.to reranker latency](https://dev.to/gabrielanhaia/rerankers-and-the-latency-budget-when-cross-encoders-are-worth-it-3efc)). A caveat applies to all of this: no measured hybrid-over-BM25 gain exists on a corpus of sub-100-token notes; every number is from passages, so the first experiment on AutoMemory's own data decides whether vectors earn their place.

For the document library, the best 2026 chunking benchmark (36 strategies, six domains, five embedders including potion models) found paragraph-group chunks of two paragraphs with one overlap best at nDCG@5 ≈ 0.459, adaptive 50–200-token chunks second at 0.441, and tiny fixed character chunks worst at 0.244 ([arXiv 2603.06976](https://arxiv.org/html/2603.06976v1)). The recipe for Markdown is to index at heading-section level, merge sections under about 50 tokens into their parent, cap at 200–400 tokens with one paragraph of overlap, and serve the enclosing tier rather than the fragment, since serving 43-token fragments is why semantic chunking came last on answer accuracy in one vendor test ([PremAI guide](https://blog.premai.io/rag-chunking-strategies-the-2026-benchmark-guide)). Notes stay one chunk each. The L0/L1/L2 tiering AutoMemory already has matches OpenViking's design, but OpenViking generates abstracts with an LLM; the LLM-free equivalent is title line, outline and full text.

Decay deserves its own ablation. FadeMem and YourMemory both report gains from exponential decay modulated by importance and access count, but on self-built benchmarks, and half-lives quoted in the field range from 72 hours to 30 days with no principled basis ([FadeMem](https://arxiv.org/html/2601.18642v2); [Nowledge](https://nowledge.co/blog/memory-decay-temporal)). Against that stand the two controlled ablations where decay hurt. The reconciliation is to give decay a floor (never below 0.2–0.3) or make it additive so an exact match on an old fact still surfaces, to set per-kind half-lives (decisions and preferences long, task-status notes short), and to let "last confirmed or accessed" reset it, which costs one timestamp column and is what Copilot's reinforcement does deterministically.

## Trust tiers must cap, sync must compact, exports must carry evidence

The poisoning literature has converged on an uncomfortable finding: content screening does not work. In the "Utility Under Attack" study, poisoning 1.2% of a LongMemEval corpus with plainly worded false assertions cut accuracy from 0.850 to 0.300; a four-stage write-time screen caught 83% of indirect prompt injections but **rejected 0 of 360 poisoned memories**; provenance-weighted retrieval at the shipped weight was indistinguishable from no defense (p=0.80); and a weight strong enough to exclude untrusted content raised accuracy from 0.317 to 0.700 on a mixed corpus but drove evidence recall to zero when the answer-bearing item was itself untrusted ([Utility Under Attack](https://arxiv.org/abs/2608.21230v1)). The authors recommend bounded occupancy constraints, caps on how many untrusted items may fill the retrieved set, over additive penalties. MPBench's detector comparison agrees: the best prompt-injection detector caught 67.7% of attacks at 1% false positives but only 42.5% of weak-signal attacks, and another flagged 53% of benign text ([MPBench](https://arxiv.org/html/2606.04329v1); [ICML 2026 listing](https://icml.cc/virtual/2026/67964)). A trust-score sanitiser in an EHR study behaved as "a confidence filter not a security filter", accepting 54 poisoned entries at trust 1.0 on one model and rejecting everything on another; the same study found that the mere presence of six relevant legitimate memories dropped MINJA's attack success from 62% to 6.67%, and that success rose with retrieval k from 6% at k=3 to 38% at k=10 ([Memory Poisoning Attack and Defense](https://arxiv.org/html/2601.05504)). The defense with the largest measured effect, A-MemGuard at ICML 2026, cut attack success by over 95% by flagging memories whose reasoning conflicts with related memories and routing them to a separate lesson store ([A-MemGuard](https://proceedings.mlr.press/v306/wei26ac.html)).

AutoMemory already has the pieces those papers ask for: author tier, quarantine, a signed ledger. The measured gap is in how tiers reach retrieval. A linear tier weight is shown not to work; the rule should be a hard cap ("agent-claim and untrusted items fill at most N of k slots and never displace a pinned or verified item on the same key"), with the tier label printed in every returned item, retrieval k kept small for low tiers, projects seeded with verified items, and code-hash verification kept as the only promotion path from agent claim to fact. The ledger should also cover reads, logging each serve-or-refuse decision with reason and tier, which the research middleware Provem does and few products do ([Provem](https://pypi.org/project/provem/)); a hash chain alone gives "tamper evidence, not authenticated provenance", so AutoMemory's signed operations are already ahead ([Procheiron listing](https://glama.ai/mcp/servers/iuyvlp8ber)).

For conflicts across agents and machines, a CRDT engine is not justified. Loro's own maintainers argue "CRDTs are not enough" because the merge function is the easy part ([loro.dev](https://loro.dev/blog/crdt-is-not-enough)); cr-sqlite gives per-column last-writer-wins but needs nightly Rust, costs 2.5× on inserts and was judged "too early-stage for production" in late 2025 ([cr-sqlite](https://github.com/vlcn-io/cr-sqlite); [MVP Factory](https://mvpfactory.io/blog/crdts-for-offline-first-mobile-sync-automerge-vs-yjs-merge-semantics-and-the/)). Letta's shared blocks show the pragmatic shape: append is concurrent-safe, replace fails if the target changed, whole-block update can clobber ([Letta shared memory](https://docs.letta.com/guides/agents/shared-memory-blocks)). AutoMemory's signed op log is already an operation-based CRDT in the degenerate case; adding a per-field `(HLC timestamp, device id)` version gives deterministic last-writer-wins on concurrent field edits, and only semantic clashes (same key, same tier, different value, or an agent proposal against a human pin) need the review queue that already exists.

Git remains the right transport for small encrypted deltas because it is authenticated, offline and needs no service, but it has two known costs: history grows forever and file names leak. Litestream v0.5's compaction ladder (30-second, 5-minute and hourly levels, restore from "about a dozen files on average") is the model for folding deltas older than a day into encrypted snapshots ([Fly.io](https://fly.io/blog/litestream-v050-is-here/)), and the Obsidian git-encryption plugin's opaque names, where "the host only ever stores unreadable data, including file names", is the model for metadata ([Obsidian plugins](https://community.obsidian.md/plugins/vault-sync-git)). Backup needs the online backup API or `VACUUM INTO`, never a plain copy of a WAL database; one test showed a copied WAL database passing `PRAGMA integrity_check` while missing a committed row ([sqlite.org](https://sqlite.org/backup.html); [thepromptshelf](https://thepromptshelf.dev/blog/sqlite-wal-backup-before-agent-migrations-2026/)). Restore should rebuild into a temp file, run `integrity_check`, compare item counts and ledger head hash against the manifest, then swap atomically, and `sync_status` should expose the age of the last verified restore, since ops guidance is to alert on that rather than on job exit codes ([oneuptime](https://oneuptime.com/blog/post/2026-09-02-automated-backup-restore-tests/markdown)).

Portability has no standard to adopt. Letta's `.af` is the most complete agent-state file but omits archival passages and has no format version field ([agent-file README](https://raw.githubusercontent.com/letta-ai/agent-file/main/README.md)); Mem0's hosted export returns schema-shaped summaries with no history or provenance ([Mem0 export docs](https://docs.mem0.ai/platform/features/memory-export.md)); the MCP reference memory server's JSONL has no timestamps or authorship ([modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)); MIF v2.0 has five stars ([mif-spec](https://github.com/varun29ankus/mif-spec)). None carries tier, signature or verification evidence, so AutoMemory should publish its own versioned JSON Schema for the op-log export (id, content, type, scope, tier, person/device/agent author, HLC timestamps, signature, supersedes links, verification evidence, review state, ledger refs) and add a lossy Markdown-with-YAML-frontmatter rendering that Obsidian, OpenViking and MIF adapters already read. Importers for Claude Code auto memory and claude-mem's SQLite are a cheap acquisition path; Mem0 CLI and Copilot both ship bulk import, which shows the demand.

Team identity is the one place where AutoMemory's current design is wrong for its stated goal. A single BIP-39 phrase is Obsidian Sync's model, where loss of the password loses the remote vault and there are no per-device keys ([Obsidian Sync security](https://obsidian.md/help/sync/security)); it is fine for one person and unworkable for a team. Keybase's per-user key is the proven shape: device keys never rotate and sign operations, a per-person seed is boxed to each active device, revoking a device bumps the generation and re-boxes for the remaining devices, team keys rotate lazily before the next write, and a box auditor catches a stolen laptop that still holds an un-rotated team key ([Keybase PUK](https://book.keybase.io/docs/teams/puk); [Team Box Auditor](https://book.keybase.io/docs/teams/box-auditor)). SOPS shows the cheap version: wrap one data key per recipient and re-wrap when the recipient set changes ([SOPS rotation](https://oneuptime.com/blog/post/2026-03-13-how-to-rotate-sops-age-keys-without-re-encrypting-all-files-in-flux/view)). Revocation never protects history already in git, and the docs must say so. Secret hygiene, finally, is solved offline: gitleaks' MIT TOML rules (140+ rules, composite rules since v8.28.0, now feature-complete) can be evaluated with the `regex` crate at write time, redacting to `[REDACTED:<rule-id>:<sha256 prefix>]` so the ledger proves what was removed without storing it ([gitleaks](https://github.com/gitleaks/gitleaks); [detect-secrets](https://github.com/Yelp/detect-secrets)).

## The improvement plan, ordered by evidence and effort

The table ranks changes by the strength of the evidence behind them and the size of the diff, and names the measurement that would confirm each. The first measurement enables all the others, which is why it comes first even though it changes no behaviour.

Three things in this list are deliberately absent. Graph memory buys about 2 points at 2–3× cost ([Mem0 paper](https://arxiv.org/html/2504.19413v1)); cross-encoder reranking on the hook path is negative or unmeasured; and LLM-driven ADD/UPDATE/DELETE reconciliation is the design the market leader abandoned. An LLM-written consolidation pass, the one LLM use with strong evidence, can remain an opt-in on top of the deterministic nightly pass once it is configured.

## Conclusion

The research reframes the competitive question. Mem0, Zep, Supermemory and Hindsight compete on vendor-run LoCoMo scores that third parties cannot reproduce, on a benchmark whose judge accepts most wrong answers; claude-mem competes on volume of captured observations, which the coding benchmarks identify as the main cause of failure. AutoMemory does not need to win that game. It needs to show, on a coding benchmark with confidence intervals, that a small set of hash-verified records injected under an occupancy cap raises resolve rate without raising cost, something no system has yet demonstrated, since even the oracle condition in VibeMemBench could not clear zero. If that experiment comes out positive, AutoMemory has the only honest number in the category; if it comes out flat, the write-policy and token reductions still make it the cheapest and safest option, which is what the complaint data says users actually want.

The deeper implication is that the memory problem for coding agents has moved from retrieval to governance. Ranking misses are 1.3% of failures; staleness, pollution, poisoning and authority are the rest, and every one of those is a property of who wrote a record, whether it still matches the code, and how much of the context window it is allowed to occupy. Those are exactly the primitives AutoMemory already encodes as tiers, hashes, locks and a signed ledger. The work ahead is to make them bite at retrieval time, to re-check them on a schedule, and to carry them intact through export, sync and key rotation, so that the trust a record earned on one machine survives on the next.
